# 运维指南

## 推荐运行模型

当前实现适合单主机、单进程、受控访问环境：

```text
客户端 → TLS/访问控制反向代理 → 单个 Node.js 进程 → data/app.json
                                      └────────────→ DeepSeek/验证服务
```

不要让多个进程或容器同时写同一个 `data/app.json`。内存请求限制、请求日志和轮询游标也无法跨实例协调。

## 启动与停止

前台启动：

```bash
npm start
```

生产环境可使用操作系统服务管理器或可信进程管理器，至少应具备：

- 固定工作目录为项目根目录；
- 注入受保护的环境变量；
- 异常退出后有界重启；
- 标准输出和错误输出进入受控日志；
- 停止前给活动请求合理的排空时间。

项目没有内建守护、日志文件轮换或优雅关闭编排。更新或备份前应先从入口摘流，再停止进程。

## 健康检查

最轻量的应用检查：

```bash
curl --fail http://127.0.0.1:3000/api/me
```

未登录时仍应返回 `200` 和匿名载荷。该检查证明进程和本地路由可响应，但不验证：

- 数据库可完成写入；
- DeepSeek 登录或 completion 可用；
- PoW、验证码和附件上传链路正常；
- 某个 API Key 或账号仍有效。

更完整的合成检查可使用专用低权限 Key 调用 `/v1/models`，但这会增加 Key 当日使用量并受请求限制影响。不要把真实生成请求设为高频健康检查。

## 反向代理要求

至少配置：

- HTTPS 与安全 TLS 配置；
- 只接受预期 Host 和来源；
- Node 端口不直接暴露公网；
- 请求体限制与应用的 110 MiB 上限协调；
- SSE 路径禁用响应缓冲和压缩转换；
- 读取超时足以覆盖长推理、30 秒频繁发送重试和多次恢复；
- 连接数、请求速率和慢客户端保护；
- 必要的安全响应头。

Chat Completions 流式请求和 `/proxy/chat/completion` 都使用 SSE，不需要 WebSocket。反向代理若缓存、聚合或提前关闭 SSE，会破坏实时输出与自动恢复体验。

## 文件权限

服务账号只需要读取源码和静态资源，并写入 `data/`。建议：

- `.env` 仅服务账号可读；
- `data/` 仅服务账号可读写；
- 源码目录不允许服务进程修改；
- 备份使用独立受控目录并加密；
- 不以系统管理员/root 身份运行应用。

## 日志与监控

### 进程日志

服务当前主要把启动信息和未捕获运行信息写到标准输出/错误。由外部服务管理器负责采集、访问控制、轮换和保留。

### 管理台请求日志

应用在内存中保留最多 500 条请求元数据。普通用户只看自己的记录，管理员可看全部。字段包括时间、方法、路径、模型、所有者、账号、状态、耗时和脱敏错误。

这些日志重启即丢失，不适合作为审计系统。若在反向代理记录请求，必须过滤 `Authorization`、Cookie、请求体和查询参数中的秘密。

### 建议监控

- 进程存活与重启次数；
- HTTP 4xx/5xx、429 和 502 比例；
- SSE 活跃连接数与连接时长；
- 上游认证、验证码、PoW、恢复/继续上限错误；
- `data/app.json` 大小、修改时间与磁盘余量；
- Node 进程内存、CPU、事件循环延迟和文件句柄；
- 账号可用数量和 token 刷新失败。

## 备份与恢复

一致备份流程：

1. 从入口停止新请求。
2. 等待活动请求完成。
3. 停止 Node 进程。
4. 加密复制 `data/app.json` 与必要配置。
5. 记录当前 Git 提交 ID。
6. 重启并执行健康检查。

恢复和完整重置步骤见[数据存储与清理](data-storage.md)。备份文件包含上游 token 和本地会话，应按生产秘密处理。

## 升级

推荐顺序：

1. 阅读目标版本变更并在隔离环境运行 `npm test`。
2. 备份数据库和配置，记录当前提交。
3. 摘流并停止服务。
4. 更新源码；不要覆盖 `.env` 或 `data/`。
5. 再次运行测试和语法检查。
6. 启动服务；首次读取可能迁移并重写数据库。
7. 验证匿名健康、登录、账号状态、模型列表和一条流式请求。
8. 保留迁移前备份，直到观察期结束。

回滚代码时不要直接使用已经由新版本迁移过的数据库。应同时恢复与旧代码匹配的备份副本。

## 容量与扩展

当前瓶颈与边界：

- 状态读写每次解析或覆盖整个 JSON 文件；
- 长 SSE 和上游恢复会占用连接；
- 110 MiB 请求体可能带来显著内存占用；
- 用户限流、日志和轮询只在内存；
- 没有多进程一致性或任务队列。

需要水平扩展、高可用或严格事务时，应先把状态、会话、限流、日志和轮询游标迁移到支持并发的外部系统，再部署多实例。仅把 JSON 文件挂载到共享卷不是可行扩展方案。

## 常规清理

确认服务停止后，可清除不会影响源码的本地产物：

- `.playwright-cli/`
- `.playwright-mcp/`
- `output/`
- `coverage/`
- `playwright-report/`
- `test-results/`
- `*.log`、`*.tmp`、缓存目录

这些路径已由 `.gitignore` 覆盖。删除前仍应确认其中没有需要保留的诊断证据。

## 事件处理

### 上游接口变化

症状通常是 401/403、验证码增加、PoW 失败、SSE 事件结构变化或白名单路径返回异常。

1. 保留脱敏后的状态码、响应头和短错误预览。
2. 检查 `DEEPSEEK_API_VERSION`、客户端版本和 PoW WASM 地址。
3. 用一个隔离账号复现，避免批量触发风控。
4. 暂停自动重试，防止扩大影响。
5. 修复协议解析后运行全部测试，再逐步恢复流量。

### 数据库损坏

1. 立即停止进程，避免继续覆盖。
2. 复制损坏文件用于诊断。
3. 验证 JSON 语法和最近磁盘/进程异常。
4. 从与代码版本匹配的备份恢复。
5. 没有备份时只能重置；上游账号和本地 Key 需重新绑定或创建。

### 凭据泄露

先撤销和轮换秘密，再处理文件与历史。完整顺序见[安全与隐私](security-and-privacy.md)。
