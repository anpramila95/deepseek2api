# 安全与隐私

## 定位

deepseek2api 是面向受控环境的网关，不是开箱即用的公网安全产品。它会代理高权限上游会话，并在本地保存敏感状态。部署者必须自行负责网络隔离、TLS、秘密管理、访问审计和合规性。

## 已实现的保护

### 数据最小化

- 默认 `PERSIST_ACCOUNT_CREDENTIALS=false`，不持久化 DeepSeek 原始登录名和密码。
- 新绑定账号只有在上游确认 `training_allowed=false` 后才保存。
- 展示层对邮箱、手机号和一般标识做掩码。
- API Key 明文默认由 24 字节随机数生成，只在创建响应中返回一次；磁盘保存 SHA-256 哈希和预览。
- 旧数据库读取时移除遗留 API Key 明文，并按当前凭据策略清理账号字段。

### 请求与响应边界

- DeepSeek 原生代理只允许源码中的静态路径白名单。
- 用户账号和 Key 按所有者隔离；管理员是特权角色。
- 代理响应移除上游 `set-cookie` 和 hop-by-hop 头。
- 错误返回前会掩码 Bearer、常见 token/密码键值、邮箱和手机号，并限制长度。
- 用户可配置并发与每分钟请求限制。

### 会话与删除

- 管理台 Cookie 使用 `HttpOnly`、`SameSite=Lax`，有效期 7 天。
- 禁用用户会删除其现有会话。
- 无痕模式仅在响应确认完整后删除上游会话，避免把失败或可恢复的会话误删。

## 仍会保存或传输的敏感数据

即使采用默认设置，`data/app.json` 也可能保存上游 token、本地会话 ID、设备档案、邀请码、验证码密钥和可关联标识。账号绑定时，登录凭据会在进程内存中存在并通过 TLS 发送给 DeepSeek。

启用验证码自动处理时，验证码相关内容可能发送给配置的第三方服务或视觉回退账号。启用前应评估该数据流、服务条款和所在地区的合规要求。

浏览器页面默认连接 Google Fonts 与 jsDelivr CDN。相关提供方能观察资源请求元数据；离线或高安全环境应改为自托管资源并配置内容安全策略。

## 已知安全限制

### 网络层

- Server 没有内置 TLS。
- 代码只指定端口，可能监听所有网络接口。
- `Access-Control-Allow-Origin` 当前为 `*`。
- 没有可信代理、来源域名或 Host 白名单配置。
- 没有内置防火墙、IP 限制或登录防爆破。

### Cookie 与浏览器安全

- 会话 Cookie 没有 `Secure` 属性；必须在可信 HTTPS 反向代理和受控网络后使用。
- 没有显式 CSRF token；`SameSite=Lax` 只能降低部分跨站请求风险。
- 没有 CSP、HSTS、`X-Content-Type-Options`、frame 限制等完整安全响应头。
- 外部 CDN 脚本没有 Subresource Integrity。

### 凭据与哈希

- 管理员凭据来自环境变量，并使用普通字符串比较。
- 本地用户密码使用随机盐加 SHA-256，但不是 Argon2、scrypt 或 bcrypt 这类密码专用慢哈希，也没有强制长度或复杂度。
- 本地 API Key 使用直接 SHA-256。服务生成的 Key 熵足够高，但允许调用方提交自定义 `plainKey`；弱自定义 Key 会降低安全性。
- 会话 ID 是 UUID，数据库中以明文保存。

### 运行与存储

- JSON 文件写入没有事务、原子交换、加密或跨进程锁。
- 请求限制、日志和轮询状态只在单进程内存中，重启可重置；多实例之间不共享。
- 默认无邀请码注册；新数据库暴露到不可信网络时，任何访问者都可能注册。
- 服务端请求与套接字超时为无限，恶意慢请求可能长期占用资源。
- 请求体上限为 110 MiB，反向代理和主机必须配套限制资源。

## 部署前检查表

- [ ] 只允许受信任网络或 VPN 访问服务。
- [ ] 用反向代理终止 TLS，并确保上游到 Node 进程的链路可信。
- [ ] 限制监听范围、入站端口、Host 和允许的来源。
- [ ] 在反向代理补充 HSTS、CSP、防点击劫持和 MIME 嗅探保护。
- [ ] 为 `.env` 和 `data/app.json` 设置最小文件权限与加密备份。
- [ ] 设置高熵管理员密码；不需要管理员时保持两个变量为空。
- [ ] 尽快开启邀请码注册，避免开放注册。
- [ ] 使用服务生成的 API Key，不使用弱自定义 Key。
- [ ] 保持 `PERSIST_ACCOUNT_CREDENTIALS=false`，除非有明确且受控的业务需要。
- [ ] 谨慎启用验证码第三方服务，并单独保护其密钥。
- [ ] 自托管前端第三方资源或接受其供应链与隐私风险。
- [ ] 维持单实例部署，并设置进程、连接、请求大小与速率限制。
- [ ] 定期验证 `.env`、`data/app.json`、日志和测试产物未进入 Git。

## 密钥泄露处置

1. 隔离服务并保存必要的取证副本。
2. 删除并重建受影响的本地 API Key。
3. 在 DeepSeek 侧撤销或退出受影响会话，必要时修改账号凭据。
4. 轮换管理员密码和验证码服务密钥。
5. 删除全部本地登录会话；最彻底方式是停服务后重置数据库。
6. 检查 Git 历史、CI 日志、进程日志、备份和截图是否含秘密。
7. 恢复服务后限制网络范围并监控异常调用。

仅删除工作区文件不能清除已推送的 Git 历史或外部日志。如果秘密曾提交，应先轮换秘密，再按托管平台流程重写历史并通知所有协作者重新同步。

## 隐私语义边界

“无痕”仅指响应完成后尝试删除 DeepSeek 上游聊天会话，不代表：

- DeepSeek 或其他服务没有保留服务器日志；
- 本地请求元数据从内存立即消失；
- 调用方、反向代理或网络设备没有日志；
- 法律意义上的删除请求已经完成。

部署者应根据自身数据分类、保留期限和适用法律建立独立制度。
